# Figma Local Bridge デザイン生成スキル

Figma Local Bridge は Figma Plugin API を WebSocket 経由で操作する。無料プランでも回数制限なしで書ける代わりに、
**Figma デスクトップで開発用プラグイン「Figma Local Bridge」を開いている間だけ**動く。
品質を決めるのは、値の出典（実 DOM・CSS）と、検収を機械の検査で行うこと。

## 0. 接続

1. リレーを起動する: `tmux has-session -t figma-relay || tmux new-session -d -s figma-relay -c <repo> "bun run src/socket.ts 2>&1 | tee -a /tmp/figma-relay.log"`。起動後は `lsof -nP -iTCP:3055 -sTCP:LISTEN` で待ち受けを確かめる（tmux に送ったコマンドが実行されないまま残ることがある）。
2. デスクトップ Figma で対象ファイルを開き、プラグイン「Figma Local Bridge」を起動する（クイックアクション ⌘/ →「Figma Local Bridge」→ Enter）。チャンネル名の既定は `figma-local-bridge`。
3. **プラグインは前面のタブとしか通信しない**。プラグインの窓を閉じる・別タブを前面にすると黙って切断される。`join` はプラグインが無くても成功するので、接続の証拠にしない。
4. **書き込む前に対象ファイルを確かめる**: `dump_tree`（maxDepth 1）で現在のページの最上位ノード名を読み、想定どおりのファイルかを照合する。複製ファイルは node ID を引き継ぐので、ID の一致はファイルの同一性の証拠にならない。
5. **接続が切れたら止める（唯一の決まり）**: 命令がタイムアウトしたら、リトライを重ねず作業を止める。委任された作業者は親へ報告する。会話中のエージェントは、リレーの待ち受けと、プラグインの窓が開いて前面にあるかを確かめ、直せない場合は本人に頼む。接続断の間はすべての命令が空振りするので、「飛ばして続行」はしない（7/16 の誤書き込み事故の再発防止）。
6. `code.js` を変えたらプラグインを開き直す（クイックアクションで再実行すると読み直される）。`server.ts` の変更は MCP クライアントの再起動で反映される。
7. **本人の画面を奪わない**: 書き込みは Figma の窓が後ろにあっても進む（前面のタブが対象ファイルであれば良い）。画面を奪うのはプラグインの開き直しの数秒だけなので、開き直したら直前に前面だったアプリへ戻す。閲覧のみの参照ファイル（講座の既存デザインなど）は、デスクトップ版で開かず、Orca の内蔵ブラウザ（`orca tab create --url <figma URL>`、`orca snapshot` でレイヤーを選び `orca keypress --key "Shift+2"` で拡大、`orca screenshot`）で読む。ディスプレイが消灯すると Figma の処理が大きく間引かれるので、長い組み立ての間は `caffeinate -d -t <秒>` を付け、終わったら自分の起動したものだけ止める。

## 0.5 運用標準（キャンバス）

1. 新しいデザインは新しいファイル（ドラフト）に作る。既存ファイルに相乗りしない。
2. ページは `Design`（画面）と `Components`（部品のマスター）。無料プランは1ファイル3ページまで。講座の既存のデザインファイルと形式をそろえる時は、その形式（§1 の `--layout course`：1ページに `コンポーネント` の枠）を優先する。
3. 標準フレームはモバイル 375×667 / デスクトップ 1366×768。幅は厳守し、ページ全体を描くカンプは高さだけ中身に合わせて伸ばす。
4. 並び順は「モバイルの各ページ → デスクトップの各ページ」。フレームの間隔は 100px。
5. ファイル名はプラグインから変えられない（`figma.root.name` は読み取り専用）。名前の変更は Figma の画面で行う（左欄のファイル名をダブルクリック → ⌘A → 自分でクリップボードに入れた名前を ⌘V → Enter → 窓の題名で確認）。画面操作の道具の「文字を貼る」機能は、クリップボードに残っていた本人の文章まで貼ることがあるので使わない。クリップボードは作業後に元へ戻す。

## 1. コードがある画面を Figma に起こす（標準手順）

目測で組まない。動いているアプリを実寸で測り、そのまま Auto Layout・部品・変数に変換する。スクリプトは `scripts/` にある。

1. アプリを起動する（教材のフォルダを汚さないよう、作業用に複製してから `npm install`）。
2. 画面一覧を JSON にする: `[{"name":"home","path":"/","label":"記事一覧（トップ）"}, ...]`
3. 実測する: `node scripts/dom-extract.mjs --base http://localhost:5173 --out <dir> --screens screens.json --components <React部品名,...>`
   各画面×幅（375/1366）について、要素の箱・計算済みスタイル・文字・画像・SVG と、ページ全体の画面写真を保存する。横スクロールの箱の中で画面外にある要素も測る。
   ブラウザの高さは標準（667/768）のまま測る。sticky や画面の高さで決まる要素（管理画面のサイドバー等）は、ページの先頭で見える大きさで描かれ、名前に「sticky・上から56px・高さは画面の高さ−56px」のように書かれる。`--full-height`（ブラウザの高さをページの高さに合わせる）はその要素がページ全体に伸びて見えるので、生徒向けのカンプには使わない。
4. 組み立てる: `node scripts/figma-build.mjs --extract <dir> --screens screens.json --images <public/images> --src <app/src> --out manifest.json --components BlogHeader,PostCard,... --state-components StatusBadge:Status --clean`
   - 変数（色）・テキストスタイル・エフェクトスタイルを登録し、部品のマスターを `Components` に、画面を `Design` に置く。
   - `--clean` はこのスクリプトが作ったファイルの `Design` / `Components` を空にしてから組み直す。人が手を入れたファイルには使わない。
   - `--specs-only` で Figma に触れずに組み立て指示だけを書き出せる（変換の点検用）。
5. 見比べる: `node scripts/figma-export.mjs manifest.json <png-dir>` と `python3 scripts/visual-diff.py <実画面.png> <Figma.png> <比較.png>`。差の割合と差の大きい帯が出る。
6. 検収する（§5）。

素の HTML/CSS のページ（講座の静的な段階など）は、画面一覧に `"url"` と `"naming": "class"` を書き、`dom-extract.mjs --class-components "header,post,pagination,single_meta-cat=category"` で部品の区切りをクラス名で指定する。レイヤー名は最初のクラス名（生徒が自分で書く名前。画像も `post_thumb` のようにクラス名で、クラスが無い時だけ画像ファイル名）、文字スタイル名は `22px/bold/1.6` の形になる。固定サイズの出典は、その要素に効いている CSS の規則（`.pagination_numbers { width: 40px }`）を読み取って記録する。

講座の既存のデザインファイルの形式で並べる時は `figma-build.mjs --layout course` を使う。1ページ（Page 1）に、`コンポーネント` の枠（見出しと下線、`・<名前>` の小見出しと部品。`--component-labels`）、`スタイルガイド` の枠（`--style-guide <json>`、中身は確かめた事実だけを書いた JSON）、`blog_OGP`（`--ogp <画像>`）、画面を `<名前>_SP` / `<名前>_PC` の組で横一列に置く（フレームの間隔はすべて 100px）。PC の画面には本文幅の中央のガイド線、SP には左右 16px のガイド線を付ける（画面一覧の `gridPC` / `gridSP`）。レイヤーパネルの順も講座のファイルと同じにし、部品の中の画面幅の違い（バリアント）は PC → SP の順に並べる。文字の高さの切り上げで画面の枠を伸ばす時は、高さを整数にそろえる。

変換の決まり（`scripts/dom-to-figma.mjs`。変えるときは検査も合わせて直す）:

- **余白は実測**: Auto Layout の4辺の余白と間隔は、CSS の padding・border と子の margin から求め、毎回すべて明示する。プラグインの余白の既定値は 0（7月まで 10 だった。「謎の10px」の原因）。
- **間隔がそろわない並び**: Auto Layout は子ごとの margin を持てないので、間隔が同じ連続した子を `stack-<間隔>` という枠にまとめ、どの枠でも間隔が1つになるようにする。
- **幅の決め方**: 通常の箱（ブロック要素）は親の幅いっぱい → FILL。中身に合わせて縮むのは、インライン要素・横並びの中の要素・中央寄せの縦並びの中の要素・絶対配置の要素だけ → HUG。`max-w-*` や `w-28` のように CSS で幅が決まる箱は FIXED（出典つき）。
- **最小幅**: `min-w-*` は固定幅ではなく下限。中身に合わせる（HUG）＋ Figma の最小幅にする。
- **高さの決め方**: 中身で決まる → HUG。横並びで引き伸ばされている → FILL。`h-16` などの固定 → FIXED（出典つき）。表の行は高さ固定、セルは行いっぱい。
- **縮む親の中で FILL を使わない**: 親が中身に合わせて縮む軸で、子を親いっぱい（FILL）にすると、親子が互いを待って潰れる。その軸の大きさを決める子が他にいる時だけ FILL にする。
- **外から大きさが決まる箱**: 最後の子の後ろの空きが「CSS の余白＋最後の子の margin」より大きい箱は、引き伸ばし・固定・表の列で大きさが決まっている。その空きは余白にしない。
- **色**: CSS の色トークン名の変数に結び付ける（`theme/brand`、`daisyui/base-content` など。Tailwind のクラス名と同じ名前）。変数を結び付けると塗りの不透明度が変数側の値で上書きされるので、`base-content/20` のような不透明度つきの色は `daisyui/base-content (20%)` という別の変数にする。トークンにない派生色（daisyUI がボタンの枠を5%暗くした色など）は結び付けない。
- **文字**: Tailwind の段階名のテキストスタイル（`text-sm/medium`、行の高さが既定と違えば `/leading-relaxed` など）。`white-space: pre-line` の改行は保つ。`line-clamp` は最大行数つきの文字にする。フォントにない太さは CSS と同じ規則で近い太さを使う（Noto Sans JP に SemiBold は無いので 600 は Bold）。
- **影**: `shadow-*` クラス名のエフェクトスタイル。影を持つ箱を包む枠ではクリップしない。
- **横スクロール**: 中身が横にはみ出す `overflow-x: auto / scroll` の箱は、切り抜きに加えてプロトタイプの横スクロール（overflowDirection）を設定する。
- **疑似要素の矢印**: 枠線2辺を回転させた `::before` / `::after`（ページ送りの「次へ」など）は、線の図形として描く。
- **部品**: 同じ React 部品が2回以上出るものをコンポーネントにし、画面幅で形が変わるものは `Viewport=SP/PC`、状態で変わるものは `--state-components` で `Status=公開/下書き` のような切り替えにする。呼び出し側は文字・塗り・線・画像（カードごとのサムネイル）を上書きする。マスターの説明欄に元の React ファイルを書く。
- **名前**: React 部品名 → daisyUI の部品名 → HTML のタグ名の順。間隔をそろえるためにまとめた枠は中身の名前をつなぐ（`h1 + p`）。sticky の箱と、実際に横にはみ出す横スクロールの箱は、名前に（sticky）（横スクロール）と書く。Figma の既定名（Frame 1 など）は使わない。
- **絶対配置**: 親の大きさが変わっても付いていく側に固定する（右端の▼は右基準、中央の要素は中央基準）。中身を組む間は、親の枠を実測の大きさで固定しておく。
- **出典の記録**: 各ノードに見えない付箋（shared plugin data `figma_local_bridge`）として、元の要素（`dom`）、固定サイズの出典（`sourceW` / `sourceH`）、余白の出典（`sourcePad`）を書く。検査と後の修正はこれを読む。

## 2. 手で組む・直す時の制約

| 制約 | 内容 |
|---|---|
| FILL のタイミング | FILL は Auto Layout の親に入れた後でしか設定できない。 |
| HUG の対象 | HUG は Auto Layout のフレームと文字だけ。 |
| resize と sizing | `resize` は sizing を FIXED に戻す。大きさを決めてから sizing を設定する。 |
| SPACE_BETWEEN | 間隔（itemSpacing）は無視される。 |
| インスタンスの中 | 子の追加・削除・並べ替えはできない。文字・塗り・線の上書きはできる。中の文字やフレームの resize は、応答が成功でも反映されないことがある。 |
| 名前 | `rename_node` で変えられる。`clone_node` は元の名前を引き継ぐ。 |
| ページ | `ensure_pages` / `set_current_page` / `move_to_page` で作成・切り替え・移動できる（`clear_page` はページ名の照合つき）。 |
| 影・クリップ | `set_effect` / `set_clips_content`。 |
| 画像 | プラグインは localhost にしか通信できない。画像は base64 で命令に入れて `figma.createImage` で作る（`build_tree` の `images`）。 |
| 大きな読み取り | `dump_tree` と `export_node_as_image` は結果が大きい。会話に流さず、ws 直結のスクリプト（`scripts/figma-dump.mjs`、`scripts/figma-export.mjs`）でファイルに書く。MCP からは `outputPath` を指定してファイルに書かせる。 |

既存デザインの修正は、`dump_tree` を対象のルートに1回当てて構造と出典を読み、差分だけを当てる。画面をまるごと作り直す時は、新しいファイル（または隣の新しいフレーム）に作り、本人の確認を得てから旧いものを消す。同じページに新旧を並べたまま検収しない。

## 3. 採寸の原則

- 値は画面写真の目測で決めない。コードがあれば実 DOM（`getBoundingClientRect` / `getComputedStyle`）、コードが無ければ画像のピクセルを実測する。
- 幅は border-box（`getBoundingClientRect`）を正とする。Figma のフレームも余白込みの幅。
- 画面サイズの基準（375×667 / 1366×768）を測る前に決める。`min-h-screen` の画面の高さは基準で変わる。
- 実際の描画を正とする。コード側の不具合（文字が枠からはみ出す等）はそのまま再現し、別に報告する。生徒に見せる教材のように、不具合を見せられない時は、コードの写しを直して直した版から作り、教材コードへの修正は差分ファイルとして本人に渡す（教材のフォルダは直接変えない）。
- いちばん信頼できる指標はフレームの全高の一致。画像の見比べでは 1px 程度の文字の位置ずれ（描画エンジンの違い）は差として扱わない。

## 4. 白紙から作る時の既定値

指示もコードも無い時だけ使う。間隔は 4px 単位（Tailwind の spacing）で、迷ったら 8 の倍数。文字は 48/32/20/16/14。色は中間色＋アクセント1色。角丸はカード 12、ボタン 8。ボタンは Rectangle で作らず、Auto Layout のフレーム（HUG/HUG）＋文字で作る。

## 5. 検収（完了の条件）

完了と報告する前に、次をすべて満たす。

1. `node scripts/compliance-check.mjs --manifest manifest.json`（手で組んだ時は `--roots <id,...>`）がすべて ○:
   余白10px帯 / 出典のない固定サイズ / FILL の付け忘れ / 縮む親の中の FILL / 切れる影 / 変数に結ばれていない色（変数と同じ色なのに結んでいないもの）/ テキストスタイルなし / 既定のレイヤー名 / 画面の高さの不一致。
   新しい決まりを足す時も、文章ではなくこの検査に項目を足す。
2. コードがある画面は、全画面の `visual-diff.py` を実行し、差の大きい帯を目で確かめる（文字の位置の 1px 程度のずれ以外の差を残さない）。
3. 作った本人ではない担当に、比較画像とレイヤー構造（`dump_tree` の結果）を渡し、「生徒や利用者が見て困る点」を点検させる。
4. 完了の報告には、ファイル名・ページ・画面の数、検査の結果、画像の比較の数値、本人の画面操作が要る残り（ファイル名の変更など）と、コード側の不具合を書く。本人や親に頼んだ画面操作は、実施を確かめるまで完了にしない。
